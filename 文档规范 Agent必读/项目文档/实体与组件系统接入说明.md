# 实体与组件系统接入说明

日期：2026-09-23  
适用工程：`HMP_game/`  
状态：当前实现的接入参考。验收结果以单独的验收报告为准。

## 1. 系统边界

本系统为现有 Unity `GameObject + MonoBehaviour` 玩法补充稳定身份、能力和关卡作用域；它不是 DOTS/ECS，也不会取代现有角色控制、火焰特效、题目流程或 UI。

运行时调用路径如下：

```text
关卡/迁移桥接
  → EntityScope / EntityRegistry
  → EntityHandle → GameEntity → EntityCapability
  → 现有 MonoBehaviour（例如 FireEffectController、OfficeChoiceTarget）
```

- `GameEntity` 保存稳定 `entityId`、多标签、激活目标和显式能力列表。
- `EntityScope` 拥有一次关卡运行的 `EntityRegistry`。同一 ID 可以存在于不同 Scope；句柄同时包含 Scope ID、实体 ID 和注册代次，不能跨 Scope 使用。
- `EntityScopeHost` 持有 Scope、内容根、角色绑定和命中代理。它在自身销毁或其任一内容根所属场景卸载时释放 Scope。
- `SceneBindingSet` 将本关角色名映射到实体 ID，例如 `player`、`spawn`、`primaryFire`。它不根据名称、层级或第一个查找结果做推断。
- `EntityHitProxy` 将一个或多个 Collider 显式映射到目标 `GameEntity`。命中解析先得到实体句柄，再取得交互能力。

核心代码位于：

```text
Assets/Framework/EntitySystem/Runtime/
  EntityPrimitives.cs            EntityId、EntityHandle、EntityError、EntityPose
  GameEntity.cs                  场景实体元数据
  EntityCapability.cs            能力生命周期与 IAnchorCapability
  EntityRegistry.cs              注册、查询、句柄、命中与释放
  EntityScope.cs                 一次关卡实例
  EntityScopeHost.cs             场景侧 Scope 所有者
  SceneBindingSet.cs             角色绑定
  SceneEntityInstaller.cs        内容根收集与只读校验
  EntityHitProxy.cs              Collider 显式归属
  Capabilities/AnchorCapability.cs

Assets/GameContent/Common/EntityAdapters/
  FireCapabilityAdapter.cs
  OfficeChoiceCapabilityAdapter.cs
  OfficeEntityBindings.cs
```

## 2. 内容约束

### ID、标签与能力

`entityId` 使用小写英文、数字、点、下划线和短横线，例如 `fire.office.main`。ID 在同一 Scope 内必须唯一，大小写敏感；改 GameObject 名称或层级不应改变 ID。

标签是自定义的多值分类，不能替代 Unity Tag、Layer 或能力校验。查询会按 ID 稳定排序；只有调用 `FindByTag(tag, activeOnly: true)` 时才过滤未激活对象。

能力必须显式列入 `GameEntity.Capabilities`，每个能力键和能力接口在同一实体中只能出现一次。能力组件必须与 `GameEntity` 挂在同一 GameObject。激活目标只能是实体自身或其子对象。

不要把对象名、Transform 路径、`FindAnyObjectByType` 或 `GetInstanceID` 当成实体身份；迁移后的关卡代码应从 Scope 的角色绑定、实体 ID 或句柄进入系统。

### Scope 根、角色与锚点

`EntityScopeHost.Configure(levelId, roots, bindingSet, hitProxies, autoInstall)` 的 `roots` 是本 Scope 的显式内容根。安装器会收集这些根下面的 `GameEntity`，包括 inactive 对象，并在构建索引、校验角色绑定和命中代理后才 Attach/Prepare 能力。

每个角色由 `SceneEntityBinding` 显式配置：

```csharp
bindingSet.Configure(new[]
{
    new SceneEntityBinding("player", "player.main"),
    new SceneEntityBinding("spawn", "anchor.player.spawn", true, "anchor", "origin"),
    new SceneEntityBinding("primaryFire", "fire.office.main", true, "fire", "origin")
});
```

多个角色可以指向同一实体。`required: true` 的角色、所需能力键和 `anchorSlot` 任一缺失都会阻止 Scope 就绪。`AnchorCapability` 使用显式槽位名，例如 `origin` 与 `approach`；槽位保存 Transform 引用，不能填层级路径。

### Collider 命中

每个可命中 Collider 需要一个 `EntityHitProxy`，并通过 `Configure(target, colliders)` 显式绑定。一个 Collider 在同一 Scope 只能归属于一个 Proxy。注册后的解析入口是：

```csharp
if (scope.Registry.TryResolveHit(hit.collider, out var target, out var error))
{
    // target 是不透明 EntityHandle；再按需要取得明确能力。
}
```

不要用 `GetComponentInParent` 或 `transform.root` 推测实体归属。`EntityHitProxy` 被销毁时会移除自己的 Collider 映射；目标 `GameEntity` 被销毁时会尝试注销实体及其映射。

## 3. 新增实体和能力

新增静态场景实体时，按下面顺序配置：

1. 在目标 GameObject 添加 `GameEntity`，填写稳定 ID、标签和激活目标。
2. 添加实际需要的能力组件，并将它们放入 `GameEntity` 的能力列表。
3. 对位置语义添加 `AnchorCapability`，并填入每个槽位的 Transform。
4. 若对象会被射线、点击或交互命中，添加 `EntityHitProxy` 并列出 Collider。
5. 把该实体放到本关 `EntityScopeHost.contentRoots` 的某个根下；不要依赖全场景扫描。
6. 需要关卡语义角色时，在 `SceneBindingSet` 新增 `SceneEntityBinding`；需要旧系统桥接时，在对应迁移桥接组件新增显式引用。
7. 在编辑器运行只读校验，再进入 Play Mode。

新增能力应继承 `EntityCapability`，为 `Key` 返回稳定白名单键，并在 `Validate` 检查 Inspector 引用与归属。`Attach` 只建立实体层订阅或上下文，`Prepare` 在所有实体和绑定已校验后执行；`Detach` 必须撤销本能力建立的订阅。不要在能力中查询任意场景对象、偷偷激活物体或调用旧组件的 `Awake`/`Start`。

现有首批能力包括：

- `AnchorCapability`：提供 `IAnchorCapability`。
- `FireCapabilityAdapter`：把 `FireEffectController` 暴露为 `IFireCapability`。
- `OfficeChoiceCapabilityAdapter`：把 `OfficeChoiceTarget` 暴露为 `IInteractionCapability`。这是办公室旧答题链的过渡适配器，判题仍由 `OfficeChoiceInteraction` 负责。

## 4. 动态与 inactive 实体

动态实例必须由创建者显式注册，销毁前也应显式注销。对象可以在 inactive 状态注册；注册不要求通过 `OnEnable`。

下面的示例假设 Scope 已就绪、`entity` 的 ID/能力已配置、`proxy` 已列出 Collider。它先注册实体，再注册命中代理；任一步失败时由创建者清理该实例。

```csharp
GameObject instance = Instantiate(prefab);
instance.SetActive(false);

GameEntity entity = instance.GetComponent<GameEntity>();
EntityHitProxy proxy = instance.GetComponent<EntityHitProxy>();
// 实例 ID 由创建者分配；复制同一个模板时每个实例使用不同 ID。
entity.Configure("runtime.example.001", entity.Tags, entity.ActivationTarget, entity.Capabilities);

if (!scope.Registry.TryRegister(entity, out EntityHandle handle, out EntityError error))
{
    Destroy(instance);
    return;
}

if (!scope.Registry.TryRegisterHit(proxy, out error))
{
    scope.Registry.TryUnregister(handle, out _);
    Destroy(instance);
    return;
}

instance.SetActive(true);

// 正常回收路径：先使句柄失效，再销毁创建者拥有的 GameObject。
scope.Registry.TryUnregister(handle, out _);
Destroy(instance);
```

如果创建者直接 `Destroy(instance)`，`EntityHitProxy.OnDestroy` 会清理 Proxy 的命中映射，`GameEntity.OnDestroy` 会尽力注销仍有效的注册。仍应以显式 `TryUnregister` 作为主路径，不能把销毁回调当作资源管理协议。注销或 Scope 释放后，旧 `EntityHandle` 均不可再操作新注册的同 ID 实体。

## 5. 办公室试点

办公室迁移使用 `OfficeEntityBindings`，它保留现有 `body`、`Interactor`、`OfficeFireChoiceFlow`、`GuidanceSystem` 和 `LevelFlowRunner` 的显式引用，并要求流程、Presenter、Interactor 同时启用实体桥接。

试点安装器只处理独立副本，配置以下对象：

| 语义 | 实体 ID |
|---|---|
| 玩家 | `player.main` |
| 出生锚点 | `anchor.player.spawn` |
| 办公室火源 | `fire.office.main` |
| 打印机目标 | `target.office.printer` |
| 窗户目标 | `target.office.window` |
| 入口目标 | `target.office.entrance` |
| 插排目标 | `target.office.power_strip` |

所有现有 `SceneChoiceAnchor` 也会作为独立 anchor 实体装配，以其 `anchorId` 建立桥接映射。出生点位置读取旧 `LevelBootstrapper` 的 `spawnAnchorPath`，不以当前玩家位置覆盖原关卡配置。

菜单入口：

- `Tools/Entity System/Create Office Pilot and Install`：创建 `Assets/Scenes/办公室场景-实体试点.unity`（若不存在）并装配。
- `Tools/Entity System/Install Current Office Pilot`：只重跑已打开的试点场景装配。
- `Tools/Entity System/Validate Active Scene`：按 Scope 只读校验 ID、标签、能力、角色绑定、Anchor 槽位、Hit Proxy 和内容根。
- `Tools/Entity System/Diagnostics`：打开按 Scope 分组的只读实体列表，查看 ID、标签、能力、激活状态、句柄和校验问题。

装配器不会自动执行，也不会写入正式 `Assets/Scenes/办公室场景.unity` 或 VFX。任何已加载场景存在未保存修改时，安装器会拒绝执行，不会替用户保存。

现有编辑器打开时，可在项目 `Library/EntityValidation.request` 写入一行 `install`。`EntityValidationRequests` 会在编辑器不处于编译/更新状态且没有脏场景时执行安装；状态写入 `Library/EntityChecks/EntityValidation.status`。空请求、脏场景请求和未知请求会被消费并标记为 `BLOCKED`，不会在稍后自动执行。

## 6. 停止与真正重开

`LevelFlowRunner.StopLevel()` 会停止当前流程、取消问题和路线，并调用 `LevelBootstrapper.ReleaseEntities()` 释放实体 Scope。`EntityScopeHost` 在自身销毁、显式 `DisposeScope()` 或内容场景卸载时也会释放 Scope。

实体注册重建不等同于恢复火焰、门、拾取物等全部游戏状态。实体试点的真正重开入口是 `LevelFlowRunner.RestartLevel()`：在实体桥接启用时先停止并释放旧 Scope，再以单场景方式重新加载该训练场景，让新的 `LevelBootstrapper` 创建新的 Scope。不要以再次调用 `Begin` 代替重开。

## 7. 暂时保留的旧系统

当前迁移没有重写以下系统：

- `FireEffectController` 的火焰表现、VFX 实例化和冻结逻辑；适配器只提供受限消防能力入口。
- `OfficeChoiceInteraction`、`OfficeChoiceTarget`、讲评和结算的实际答题判定链。
- `Interactor` 的非办公室目标交互、拾取、手势、座椅和放置逻辑。
- `GuidanceSystem` 的网格规划与路线渲染。
- `LevelFlowRunner` 的阶段编排、计时、得分和结算。
- 场景资源加载、Lua、全局 Event Bus 与完整多火源喷射选择。

新关卡应仅在需要的实体上采用实体系统；未迁移对象仍按原有 MonoBehaviour 流程运行，避免同一交互或火焰逻辑被两条链路同时驱动。
