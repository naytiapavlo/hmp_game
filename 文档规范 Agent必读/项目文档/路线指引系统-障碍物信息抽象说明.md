# 路线指引系统——障碍物信息抽象说明

> 状态：已实现（对应代码 `HMP_game/Assets/scripts/指引/`）
> 上游文档：《路线指引系统架构设计.md》
> 本文回答三个问题：障碍物信息抽象是什么、数据长什么样、换新场景怎么接入。

---

## 一、抽象本体：一个接口 + 一种数据格式

障碍物信息抽象 = **`IObstacleProvider` 接口**（谁提供障碍）+ **`OccupancyGrid` 格式**（障碍长什么样）。规划器 `RoutePlanner` **只认识 OccupancyGrid，完全不认识 Unity 场景**——这就是"抽象"的边界。

```csharp
public interface IObstacleProvider
{
    // 用障碍数据构建一张 XZ 平面占用栅格
    OccupancyGrid BuildGrid(float cellSize, Bounds area);

    // 障碍变了（门开了、家具挪了）时通知规划侧重建
    event Action ObstaclesChanged;
}
```

## 二、数据格式：OccupancyGrid（占用栅格）

本质是一张**俯视的"像素图"**：每个格子代表地面上 cellSize×cellSize（默认 0.25m）的一块，值只有两种——**空 / 挡**。

```
字段：
  CellSize = 0.25f        每格边长（米）
  Origin   = (minX, minZ) 栅格左下角对应的世界坐标
  Width × Height          X/Z 方向格数（办公室实测 408×408）
  bool[] blocked          一维数组，[z*Width + x] = 该格是否阻挡
```

示意（5×5 栅格，█=桌子投影，·=可通行）：

```
世界坐标 → 格子：cx = ⌊(x - Origin.x) / 0.25⌋，cz 同理（z 方向）

      z↑   ·  ·  ·  ·  ·
          ·  █  █  █  ·        桌子包围盒投影 → 连续标记
          ·  █  █  █  ·
          ·  █  █  █  ·
          ·  ·  ·  ·  ·   → 起点(3,0) 终点(3,4)
                                A* 会给出绕右侧的路径
```

配套操作原语都在 `OccupancyGrid` 类里：

| 原语 | 用途 |
|---|---|
| `BlockRect` | 把一个世界 XZ 矩形标记为阻挡（碰撞体包围盒 + 外扩后调用） |
| `IsBlocked` | 查格子（出界按阻挡处理，防路径绕出规划区域） |
| `HasLineOfSight` | Bresenham 格线直线检查，用于路径平滑 |
| `FindNearestFree` | 环形搜索最近空格，救"起点/终点落在障碍格里"（如贴墙目标） |

## 三、默认实现：SceneObstacleScanner 怎么从场景生成这张图

`SceneObstacleScanner : IObstacleProvider` 是 Unity 场景的默认提供者，采集规则四条：

| 规则 | 内容 | 原因 |
|---|---|---|
| 来源 | 「场景」根下所有 **Collider**（含未激活） | 办公室 630 个静态碰撞体，物理形状即真实阻挡 |
| 高度过滤 | 顶面 **< 0.35m** 不算挡（地毯/门槛）；底面 **> 1.8m** 不算挡（天花板/吊件） | 玩家 stepOffset=0.3 能跨矮物；天花板不投影否则整图封死 |
| 面积过滤 | 单个障碍投影 **> 40m²** 忽略并记名 | 楼板/建筑外壳的整体包围盒不是真家具（曾把 97% 格子封死） |
| 交互物排除 | 挂 DoorController / InteractableRelay / PickupItem 的不算 | 门会转、道具会被拿走，不是静态障碍 |

流程：每个通过过滤的碰撞体取世界 AABB → 外扩 0.1m（胶囊半径余量）→ `BlockRect` 打进栅格。整图缓存，门开合等变化走 `ObstaclesChanged` 事件触发重建（外部调 `NotifyObstaclesChanged()`）。

## 四、完整调用链

```
GuidanceSystem.ShowRoute(目的地, 名称)
   └─ EnsureGrid()
        └─ scanner.GetSceneBounds()            // 先问覆盖范围
        └─ scanner.BuildGrid(0.25, area)       // 场景碰撞体 → 栅格（一次构建，缓存）
   └─ RoutePlanner.TryPlanPath(起点, 目的地, grid, out waypoints)
        └─ A* 只在 bool[] 上跑，输出世界坐标路点   // 纯 C#，可单测
   └─ FloorArrowRenderer 铺箭头
```

## 五、换新场景的三种接入方式（零逻辑代码）

1. **零成本**：场景里有「场景」根 + 静态碰撞体 → 直接用 `SceneObstacleScanner`（GuidanceSetup 装配工具自动挂）；
2. **手写数据**：某关想要人为禁区（考核用不可进入区）→ 写一个十几行的自定义 Provider，在 `BuildGrid` 里对若干矩形调 `BlockRect`，不依赖碰撞体；
3. **外部数据**：障碍来自策划表格 / JSON / 另一套物理系统 → 同样只需实现 `BuildGrid` 把数据灌进栅格。

## 六、选型依据（为什么不是别的格式）

- **对比直接传 `List<Collider>`**：规划器会耦合 Unity 物理组件——没法脱离场景做单元测试，也没法接非碰撞体数据源；
- **对比 NavMesh**：NavMesh 是编辑期烘焙、场景自带，数据流方向与"障碍作为入参"的契约相反，且 630 个非凸碰撞体需逐个加静态标记走烘焙管线；
- **栅格的代价与演进**：0.25m 精度、纯平面（无高差/多层）。办公室够用（3.2 万格、A* 毫秒级、整图构建 <10ms）；将来若有立体关卡，`OccupancyGrid` 加一层 Y 索引即可演进，接口不变。

## 七、一句话总结

**把"哪里不能走"从"场景里有什么组件"压缩成一张布尔方格图——提供者（IObstacleProvider）负责怎么填，规划器（RoutePlanner）只管在图上找路，两边通过 `BuildGrid(cellSize, area)` 这一个调用解耦。**
