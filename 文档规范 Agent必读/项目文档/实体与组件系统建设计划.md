## 1. 本阶段目标

先建立一套轻量的“实体标识 + 能力组件 + 关卡作用域注册 + 场景绑定”系统，为后续 Level Runtime、Lua、Event Bus 提供稳定对象访问边界。

完成后，调用方应能够表达：

```text
获取本关的 player.main
获取任务绑定的 primaryFire
查询本关所有 fire 标签实体
读取出生锚点的位置
启用或禁用某个实体
检查实体是否具备交互/火势/锚点能力
通过能力接口执行操作，不查模型层级
```

本阶段成功的标志是：改物体名称、移动其场景层级，不再破坏已迁移的关卡引用；多个相同 Prefab、多个火源能被准确区分；关卡退出和重开不会遗留有效的旧句柄或订阅。

## 2. 范围与设计原则

### 2.1 首期必须完成

- Entity ID、多个自定义 Tag、实体句柄。
- 每个关卡运行实例独立的 EntityRegistry。
- GameEntity 场景组件，以及显式能力组件清单。
- 能力契约、适配器注册、查询、就绪检查与释放协议。
- SceneEntityInstaller：从明确的场景内容根收集并安装实体，包含 inactive 对象。
- SceneBinding：关卡语义角色到实体 ID 的映射与能力要求校验。
- Collider/交互命中对象到实体的显式映射。
- Inspector 校验、整场景校验、最小诊断列表与自动化验收。
- 出生点、单个办公室火源、四个题目目标的渐进接入。
- 动态实体的显式注册/注销基础接口；用测试 Prefab 验证，不建设资源加载平台。

### 2.2 本阶段不展开

- 不引入 DOTS/Unity Entities，不构建数据导向 ECS、统一 Tick 调度或查询语言。
- 不同时开发完整 Lua Runtime、Event Bus、Addressables、任务/计分/存档系统。
- 不把所有 MonoBehaviour 改成新继承体系，不将所有模型子物体都实体化。
- 不重写灭火算法、角色控制、教官 UI 或整套关卡状态机。
- 不承诺已有任意物体都能无损原地复位；首期完整重开使用场景重载，局部 reset 以后按能力定义。
- 不允许脚本用字符串任意反射调用 Unity 方法，或运行时任意 AddComponent 来拼装玩法。

### 2.3 复用现有 Unity 组件

Entity 是玩法对象的身份与能力入口；Unity GameObject 继续承载场景对象，MonoBehaviour 继续实现具体行为。

```text
关卡调用方（现阶段 C#，未来 Lua）
             ↓
EntityFacade / SceneBinding
             ↓
EntityRegistry（当前关卡运行实例）
             ↓
EntityHandle → GameEntity → 能力接口
                              ↓
                         适配器组件
                              ↓
          现有 FireEffectController / OfficeChoiceTarget 等
```

“组件化”的含义是按能力组合，例如一个对象同时具备位置、交互和火势能力；不要求先构建 FireEntity、DoorEntity、NPCEntity 等实体子类。

## 3. 概念与责任

| 概念 | 责任 | 不负责 |
|---|---|---|
| EntityId | 内容中的稳定对象身份 | 场景路径、显示名称、当前运行实例身份 |
| EntityHandle | 指向一次注册的安全句柄 | 跨重开持久保存 Unity 对象引用 |
| GameEntity | 保存 ID、标签、激活目标、能力适配器引用 | 题目、得分、下一关、资源加载 |
| EntityRegistry | 注册、索引、查询、句柄验证、注销 | 创建美术资产、判定关卡通过 |
| EntityScope | 拥有一次关卡运行的 Registry、绑定与生命周期 | 充当全局静态服务定位器 |
| 能力组件 | 暴露一项明确行为/数据契约 | 引入具体关卡流程 |
| SceneBinding | 将 primaryFire、spawn 等关卡角色映射到实体 | 根据 Hierarchy 路径猜测对象 |
| EntityHitProxy | 将明确的 Collider 转发到实体句柄 | 根据射线命中自动判对错或加分 |
| EntityFacade | 验证句柄并执行有限的查询/命令 | 向未来 Lua 返回 GameObject、Transform、MonoBehaviour |

Registry 和绑定不采用静态 Instance。调用者通过 Bootstrapper 或显式序列化的 EntityScopeHost 获得本次运行的上下文。

## 4. 实体身份、标签与查询

### 4.1 稳定 ID

建议 ID 使用小写英文、数字、点、下划线和短横线，例如：

```text
player.main
anchor.player.spawn
fire.office.main
target.office.printer
target.office.window
target.office.entrance
target.office.power_strip
item.extinguisher.01
```

规则：

1. 同一个 EntityScope 内 ID 必须非空且唯一，字符串比较使用 Ordinal，不做自动大小写折叠或静默修正。
2. 同一场景内改 GameObject 名字、改层级，不改变 ID。ID 变更是内容契约变更，校验器必须报告失效的绑定。
3. 不用 GameObject.name、Hierarchy 路径、GetInstanceID 生成持久内容 ID。
4. 同一个场景供不同关卡顺序复用时可以沿用 ID，但每次运行建立新的 Scope。
5. 不同 Scope 可以存在相同 ID；实体实际查找身份是 `(scopeId, entityId)`。
6. 不同 Scope 不允许同时拥有同一个活的 GameEntity 对象。并发关卡需要独立实例；同一份场景顺序复用则先释放旧 Scope。
7. 一个 Scope 收录多个 additive 场景时，这些场景中的 ID 也必须互不冲突；不能根据活动场景自动切换查找目标。

### 4.2 Prefab 与动态实例

- 普通 Prefab 模板不预填最终实例 ID；场景放置实例时填写 Override，动态创建时由调用者提供 ID。
- 复制场景对象导致相同 ID，应直接报错；可以提供显式“生成新 ID”编辑器按钮，不在 OnValidate 中偷偷改 ID。
- 动态临时 ID 可由 Scope 生成，例如 `runtime.extinguisher.0001`，不得写成下一次运行仍有效的内容绑定。
- 首期只支持调用者创建对象后显式注册、销毁前显式注销；创建行为与资源管理仍由原系统负责。
- 活跃 Prefab 的旧 Awake/OnEnable 可能先于注册发生。新实体系统不声称能阻止旧逻辑提前执行；动态验收使用可控 inactive 模板或无副作用的测试组件。

### 4.3 句柄失效

句柄至少携带 `scopeId + entityId + registrationGeneration`。

- 注销后再注册同 ID，旧句柄不能指向新实体。
- 重开或销毁 Scope 后，所有旧句柄失效。
- 句柄只标识对象，不能直接暴露原始 Unity 引用给关卡脚本。
- C# 模块可内部缓存接口，但必须在 Scope 释放时清理；外部 Facade 每次执行都验证句柄与组件就绪状态。

### 4.4 标签

- 使用自定义多标签集合，不占用 Unity 的单一 Tag，也不替代物理 Layer。
- 首期标签在安装期间固定，示例 `fire`、`hazard`、`interactable`、`pickupable`、`anchor`。
- 标签表示类别，能力接口表示能做什么；有 fire 标签不代表一定有 IFireCapability，不能代替能力校验。
- 默认标签查询包含已注册的 inactive 实体，可显式加 `activeOnly` 过滤。
- 查询返回快照，并按 EntityId 稳定排序；调用方不得依靠场景扫描顺序选择“第一个火源”。
- ID 精确查找和能力查找使用缓存索引，不在 Update 中重复扫描场景或调用全局 Find。

## 5. GameEntity 与组件模型

### 5.1 场景组合示例

```text
起火点 GameObject
├── GameEntity
│   id: fire.office.main
│   tags: fire, hazard
│   capabilities: [AnchorCapability, FireCapabilityAdapter]
├── AnchorCapability
├── FireCapabilityAdapter → FireEffectController（显式引用）
└── FireEffectController（保留现有实现）

办公室题目目标 GameObject
├── GameEntity
│   id: target.office.window
│   tags: interactable
├── AnchorCapability → 交互接近点/目标位置
├── OfficeChoiceCapabilityAdapter → OfficeChoiceTarget
└── OfficeChoiceTarget（暂保留旧判题链）
```

`OfficeChoiceCapabilityAdapter` 是迁移适配器，命名明确其业务来源。它不能被当作“已完成通用交互解耦”；以后实体交互与判题拆开时再替换其内部实现。

### 5.2 能力清单与所有权

- GameEntity 持有 Inspector 显式能力列表，由安装器建立能力索引。
- 适配器可持有子物体/其他组件的序列化引用，不根据任意后代 GetComponent 结果自动归属。
- 一个适配器实例只属于一个 GameEntity；共享系统（导航、UI、音频服务）通过上下文提供，不重复包装成所有实体的“私有组件”。
- 允许实体嵌套，但父实体不会自动收集子实体的能力和 Collider。
- 首期同一实体同一能力接口只能有一个提供者；重复直接报错，不引入默认优先级。
- 一个实体需要多个语义位置时，AnchorCapability 内使用明确的槽位，例如 `origin`、`approach`。每个槽位映射一个序列化 Transform；不将 Transform 路径作为槽位值。
- 首期能力集合在注册后固定。不提供任意运行时增删能力；确需重组时先注销，再重新验证注册，产生新代次。
- MonoBehaviour.enabled 只影响具体组件运行，不等于从能力索引移除。适配器必须区分“具备能力”与“当前可执行”，返回明确的未就绪/不可用结果。

### 5.3 首批能力

| 能力 | 首期范围 | 现有实现/接入位置 |
|---|---|---|
| IEntityActivation | 设置实体自身激活目标的 activeSelf；查询 activeSelf/activeInHierarchy | GameEntity 的显式 activationTarget，仅允许所属对象或其子树，不能指向 ScopeHost |
| IAnchorCapability | 读取指定槽位的世界位置/旋转值，不向脚本暴露 Transform | 出生点、题目接近点、火源位置 |
| IFireCapability | 读取/设置火势，适配已有表现冻结；必要时转发现有 VFX 参数 | FireEffectController；接口放消防模块，不放实体核心 |
| IInteractionCapability | 查询当前可交互状态和提示，接受 actor 句柄发起交互 | 首先包装 OfficeChoiceTarget/IInteractable；需要旧 Interactor 的转换仅在迁移适配器内部完成 |

不在首期暴露任意 Transform 写入接口：玩家传送继续由 Bootstrapper 处理 CharacterController 开关；拾取、刚体和门的移动由各自专用能力控制。

第二批再考虑 Pickup、Door、Seat、Extinguisher、Animation、Audio、VFX 能力。首期不为尚无调用方的系统创建空接口壳。

## 6. 生命周期与错误处理

### 6.1 显式安装流程

```text
创建 EntityScope（带 levelId 和新的 scopeId）
    ↓
从指定 contentRoots 收集 GameEntity，包含 inactive
    ↓
验证 ID / Tag / 适配器所有权 / 重复能力 / 序列化引用
    ↓
构建临时 Registry 索引
    ↓
验证 SceneBinding 和所需能力
    ↓
全部适配器 Attach(context) → Prepare()（解析依赖、订阅必要旧事件）
    ↓
全部成功后设置 Scope.Ready
    ↓
允许 Bootstrapper 定位玩家、Runner.Begin
```

- Attach/Prepare 是新适配层协议，不冒充 Unity Awake/Start，也不手动调用旧组件的 Awake/Start。
- 安装必须从明确的 contentRoots 开始；根列表重叠时同一个对象仅收集一次，不得绕过不同对象的重复 ID 检查。
- 两阶段解析：先建立全体身份/能力索引，再解析跨实体依赖，避免用 Script Execution Order 排列整个对象图。
- 构建中的索引只对安装器/适配器可见；外部查询在 Ready 前返回 ScopeNotReady。
- 适配器对尚未初始化的旧组件必须明确处理：纯引用/数据查询可以准备完成；需要旧 Awake/Start 的行为命令返回 CapabilityNotReady，或在启用后完成准备。不能为“初始化”偷偷激活原本隐藏的对象。
- 首期适配器使用同帧、无协程的准备协议。未来异步资源/脚本初始化另行扩展。
- 任一必需项失败：停止开局，反向 Detach 已附着的适配器，清空临时索引并报告错误；不允许“部分实体可用”的半开局状态。
- 动态注册遵循同样的验证、临时索引、Prepare、提交步骤；失败只回滚本次新实体，不损坏已 Ready 的其他实体。销毁前由其创建者显式注销，Scope 释放本身不接管所有 GameObject 的销毁权。

适配器的 Scope 级事件订阅在 Attach/Detach 成对处理，与旧 MonoBehaviour 的 OnEnable/OnDisable 订阅分别管理，避免重复订阅。可用简单的订阅释放集合记录本阶段新增回调；它只负责实体层自身清理，不在本阶段接管尚未迁移的全局计时和 UI 服务。

### 6.2 激活、注销、销毁

| 操作 | 注册状态 | 约定 |
|---|---|---|
| GameObject.SetActive(false) | 保留注册 | 仍可按 ID 找到并重新启用；OnDisable 不注销 |
| 关闭能力 MonoBehaviour | 保留能力声明 | 能力是否可执行由其适配器判断；不代表实体销毁 |
| EntityFacade.SetActive(true) | 保留注册 | 只改变 activationTarget；若祖先仍 inactive，不自动激活祖先，结果注明实际有效状态 |
| Unregister(handle) | 移除注册、标签与命中索引 | 先使句柄失效，再 Detach；不自动 Destroy 用户拥有的场景对象 |
| 实体 GameObject 真正销毁 | 注销兜底 | OnDestroy 尽力通知拥有它的 Scope；显式注销是主路径 |
| 子能力或 Collider 被独立销毁 | 保留实体，能力/命中映射失效 | 执行时检查 Unity 对象有效性并报告缺失，禁止返回悬空引用 |
| Scope.Dispose | 全部句柄失效 | 先拒绝新命令，再逆序 Detach、清空事件/索引/绑定；重复调用安全 |

对于从未激活的对象，不依赖 OnDestroy 一定完成清理。查询和命中解析也必须检查对象是否仍存在，发现失效项立即从索引移除；场景卸载由 ScopeHost 的显式场景所有权机制收尾。

Registry 的 Registered/Unregistered 通知采用简单 C# 事件供诊断使用，不扩建业务 Event Bus；通知发生在索引状态提交之后。通知期间的再注册/注销不允许同步重入，须返回 Busy 或由调用者下一帧重试。

### 6.3 场景卸载与重开

- ScopeHost 放在稳定管理对象上，不放进会被禁用的实体根下面。
- 首期 Scope 声明固定的场景与根集合；其中任何一个所属场景卸载，都终止该 Scope。在线增删 additive 场景留后续扩展。
- `StopLevel/Abort` 接入 Dispose；即使非正常场景卸载，Host 也要清理。
- 现有结算重试只调用 Runner.Begin。迁移试点必须改为统一重开入口：终止旧流程→Dispose→重载该训练场景→新 Scope→准备→Begin。
- 实体注册重建不等于门、物品、火势全部复位。首期采用场景重载保证基线，未来再定义各能力的状态捕获与 reset。
- 不把实体对象标记 DontDestroyOnLoad。跨关常驻服务由应用层管理，通过显式引用注入。

### 6.4 错误契约

统一返回成功/失败与结构化错误，不用 null 混淆全部情况：

```text
InvalidId / DuplicateId / EntityNotFound / InvalidHandle
ScopeNotReady / ScopeDisposed / AlreadyOwned / Busy
MissingCapability / DuplicateCapability / CapabilityNotReady
MissingBinding / MissingReference / InvalidOwner / OperationRejected
```

日志至少包含 levelId、scopeId、entityId、能力名、操作名、原因；Editor 中附可定位对象。必需绑定缺失阻止开局，可选绑定缺失只报告并交给调用方处理；不自动查找另一个“长得像”的对象兜底。

## 7. 接口草案与未来脚本边界

以下是职责级草案，实施时补齐 DTO、结果类型与接口签名，不作为现有可编译代码：

```csharp
// Registry：仅对 C# 安装器/服务开放。
TryRegister(GameEntity entity, out EntityHandle handle, out EntityError error);
TryResolve(EntityId id, out EntityHandle handle);
IsValid(EntityHandle handle);
FindByTag(string tag, bool activeOnly = false); // 稳定排序快照
TryGetCapability<T>(EntityHandle handle, out T capability);
Unregister(EntityHandle handle);
Dispose();

// Binding：当前关卡语义角色。
TryResolveRole(string role, out EntityHandle handle);

// 对关卡调用方开放的 Facade：所有操作先验证 Scope/Handle。
Get(string entityId);             // 返回不透明句柄/错误
HasTag(EntityHandle handle, string tag);
SetActive(EntityHandle handle, bool active);
GetAnchorPose(EntityHandle handle, string slot);
```

未来 Lua 只接收不透明句柄、标量和结构化值；不暴露 `TryGetCapability<T>`、反射、GameObject、Transform、GetComponent 或任意 C# 对象。Fire/Interaction 等模块以后分别注册白名单 API。实体层现在先提供可以包成这些 API 的稳定边界，不提前安装 Lua 依赖。

交互适配器把 actor 句柄转换成旧 Interactor 时，使用安装阶段明确登记的玩家绑定，不在命令中全局查找。现有 IInteractable.Interact 返回 void，因此“命令已转发”只能表示请求被接受，不能当作物品已拿起、窗已打开或任务已完成；实际完成仍读取旧玩法的明确事件/状态，后续再统一业务事件载荷。

## 8. 场景绑定与物理命中

### 8.1 SceneBinding

场景实体身份与关卡角色分开：同一个场景有两个火源，不同关卡可把 primaryFire 绑定到不同实体。

拟定数据形态：

```json
{
  "schemaVersion": 1,
  "bindings": [
    { "role": "player", "entityId": "player.main", "required": true },
    { "role": "spawn", "entityId": "anchor.player.spawn", "required": true,
      "capability": "anchor", "slot": "origin" },
    { "role": "primaryFire", "entityId": "fire.office.main", "required": true,
      "capability": "fire" }
  ]
}
```

首期以序列化 BindingSet 作为实际编辑载体，语义同上；JSON 是未来 bindings.json 的目标格式，本阶段不再新增一套运行时 JSON 加载器。之后可用序列化 DTO 导入同一个模型。

约束：role 唯一且只映射 Entity ID；无递归 alias；多个角色可引用同一实体；能力名使用白名单标识，不写 .NET 类型名。所需 Anchor 槽位也在准备期间校验。

### 8.2 Collider 与实体

- EntityHitProxy 显式引用一个 GameEntity，并登记所属 Collider 列表；允许门把手这种平级网格指向门实体。
- 每个 Collider 在一个 Scope 内至多有一个实体归属，重复代理报错。
- 不使用 `transform.root` 推断身份，也不盲目 GetComponentInParent 跨越嵌套实体边界。
- 命中结果区分原始 Collider 的诊断信息和最终目标实体句柄；原始 Collider 不直接暴露给未来 Lua。若以后引入物理命中事件，还需保留明确的命中来源与目标身份，不能只传一个含义不明的 string。
- InteractableRelay 暂时保留原来的实际执行转发；新增命中映射只提供“命中了谁”，避免一键触发两次交互。
- 旧 Interactor 在试点先解析目标实体，再由唯一适配器进入旧交互链；未迁移对象仍走旧逻辑，迁移标记保证两条路径互斥。
- 标签和注册不保证 Collider 能命中：禁用 Collider、activeInHierarchy=false、Layer 过滤仍遵循原物理行为。
- 本阶段两个火源的验收通过明确 ID/代理访问验证。灭火器完整多目标射线选择是后续消防接入任务，不能宣称注册表已自动解决现有单目标喷射限制。

## 12. 验收用例

### 12.1 EditMode：数据与契约

1. 相同 Scope 两个对象同 ID：安装失败，报告两处对象，不覆盖先注册项。
2. 不同 Scope 同 ID：分别解析到各自对象；把 A 的句柄交给 B 操作被拒绝。
3. 注销再注册同 ID：旧 generation 句柄失效；Dispose 后所有句柄失效。
4. 标签多值、排序、inactive 过滤正确；标签不赋予缺失能力。
5. 缺能力、重复能力提供者、适配器被两个实体拥有：验证失败。
6. 必需 role 缺失、目标 ID 不存在、Anchor 槽位缺失：准备失败；可选 role 缺失可报告并继续。
7. Prepare 中途失败：所有已 Attach 适配器 Detach 一次，Registry 不对外 Ready。
8. 查询快照遍历期间正常注销实体，不破坏快照；事件通知回调的同步重入按 Busy 契约处理。

### 12.2 PlayMode：真实 Unity 生命周期

1. 初始 inactive 实体可注册、查询、启用；不靠 OnEnable 注册，不因 OnDisable 丢失。
2. activationTarget 的祖先 inactive 时，不擅自激活祖先，activeSelf 与 activeInHierarchy 状态报告正确。
3. 销毁从未激活的实体后，查询不返回有效句柄；单独销毁能力/Collider 不产生悬空访问。
4. 改名及移动层级后，出生点、火源、四个题目目标、气泡仍按绑定工作。
5. 两个同 Prefab 场景实例拥有不同 ID；模板复制造成重复时明确报错。
6. 注册动态 inactive 实体→启用→注销→销毁，全程索引正确；销毁/Dispose 重复通知不抛异常。
7. 两个火源按 ID 分别切换火势，互不串联；不把此项当作多目标喷射算法验收。
8. 嵌套实体、平级门把手代理、重复 Collider 代理均符合显式归属规则；一次 E 只执行一次交互。
9. 一 Scope 包含两个场景时 ID 冲突可检出；任一所属场景卸载使 Scope 释放。独立 Scope 之间互不清理。
10. 连续重开至少 10 次，注册数与基线一致，旧句柄不可用，无累计重复回调、持有引用或旧 Scope 订阅。
11. 安装失败时 Runner 不启动，报告可定位错误；停止/退出后无实体命令再生效。

### 12.3 原玩法回归

- 办公室三题：正常作答、选择后到目标交互、超时、反馈/讲评、下一题、结算、重试、返回菜单。
- 摄像机、光标、天花板、人物显示与原逻辑一致。
- 未迁移的门、座椅、拾取、路线和灭火原型不被新增组件重复驱动。
- 原有 Setup 与新增 EntitySetup 重跑两次，实体数量、ID、绑定不漂移。
- 已知 StageTimer 缺失推进、暂停语义不统一分别记录；此阶段实体验收不能以旧缺陷为“通过依据”，也不把修复这些系统悄悄并入范围。若阻断试点回归，则单独记录最小前置修复。

## 13. 风险与约束

| 风险 | 处理 |
|---|---|
| 将 ID 系统写成另一种全局 Find | 所有调用显式限定 Scope；不用静态 Registry 单例 |
| 仅包一层接口却保留旧多方写状态 | 标记适配器过渡性质；火势状态权威仍是后续消防整合任务，不宣称已解决 |
| 不活动对象初始化顺序不可控 | 显式安装含 inactive；适配器准备独立于 Awake；必要行为返回未就绪 |
| 开局前旧组件已经自动运行 | 试点设置 runnerDriven/autoStart 等装配选项；明确哪些旧自动入口必须关闭 |
| 原地重开无法恢复全部状态 | 首期重载场景；Scope 重建不替代 gameplay reset |
| 字符串 ID 误拼和 prefab 复制冲突 | 编辑器校验、绑定选择器与运行时硬错误；不静默生成替代 ID |
| 新实体组件与旧脚本双重执行 | 试点路径互斥；保留一个实际执行者，不重复跑 Update 或重复转发 E |
| 跨程序集无法引用旧代码 | 核心只依赖契约；迁移适配器留可引用旧脚本的程序集 |
| 建设范围膨胀 | 首批仅四类能力；其余按真实关卡需求逐批接入 |

## 14. 本阶段完成定义

以下条件全部满足，才进入下一阶段 Lua/关卡流程建设：

- 身份、作用域、能力、绑定、注册与卸载行为有明确实现和测试。
- 办公室已迁移对象不再依赖 GameObject 名称/Hierarchy 路径或全局 Find 查找。
- 新增同类实体通过场景组件与绑定即可接入，不修改 Registry 或核心 switch。
- 同场景多个实体、不同 Scope、inactive、销毁、重开均通过上述验收。
- 旧接口兼容范围、未迁移模块和后续消防状态权威问题有清单。
- 交付实体系统接入说明、场景绑定示例、验收报告与本计划的完成状态更新。

后续推荐接续顺序：关卡作用域 Event Bus → 统一 Timer/控制权 → Lua 白名单 API → 将办公室编排迁入关卡包。完整 Level Runtime、资源加载与任务系统按这个对象基础继续建设。
