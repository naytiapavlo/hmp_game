# 关卡系统重构前：耦合点与复用边界

核查日期：2026-09-23。依据当前工作区运行时代码、JSON、Editor 装配代码与场景配置，以及本轮提供的《Unity 高度可定制化关卡系统需求文档》。本轮仅分析，不修改运行时代码或场景；未运行 Unity Play 验证。以下代码路径以 Unity 工程 `HMP_game/` 为基准，行号对应本次核查版本。

## 1. 结论

项目已经完成了部分内容配置化，但执行层仍然是“办公室消防三题训练流程”。问题不在于缺少 JSON，而在于通用能力、消防机制、单关规则和表现编排混在同一调用链中。

建议按三种归属拆分，再分别确定用 C#、Lua 或资源实现：

1. **统一核心**：关卡生命周期、资源与场景、实体绑定、事件、输入与控制权、计时、得分记录、UI/演出服务。
2. **可选复用模块**：消防火势/喷射/压制、场景实体选择题、第一人称持物、路线引导、教官讲评。按需加载，不让每一关强制依赖。
3. **关卡包**：题目、答案、目标对象、流程先后与分支、得分规则、通关条件、火势参数、演出资源和模型绑定。

“关卡专属”不等于“都要写 Lua”。文案和参数用配置，演出用 Timeline/资源，规则用 Lua；碰撞、射线、渲染、骨骼适配等 Unity 能力保留在 C# 模块中。

## 5. 每类内容独有的部分

### 5.1 当前办公室关卡

- **内容配置**：三道题的文案、答案、45 秒时限、7.5 分分值、教官正误讲稿、视频、提示与路线标签。
- **场景绑定**：打印机、窗户、入口、插排，对应操作目标、走近位置、气泡锚点；办公室几何、出生点、俯视机位、天花板和人物显隐组。
- **流程规则**：起火演出→第一题→前往选中目标按 E→反馈/教官→结果过渡→第二题→第三题→结算；是否复位玩家、超时记错但继续训练、每题对错导致怎样的火势结果。
- **结果定义**：三次训练全部正确才通过、实际作答与行动耗时纳入结果、讲解与加载耗时排除。

其中“选择→走到目标→操作确认”有跨关复用价值，应成为可选玩法模块；“这道题需要操作哪个目标、答案是什么”留在关卡包。

需特别注意：当前 `OfficeChoiceTarget.Interact` 调用 `owner.Complete`，后者主要完成判题和反馈。文字中的“开窗/拔插排/呼喊”不能据此认为已经存在相应真实动作、模型状态变化或 Timeline。重构应迁移实际能力，缺失表现单独补充。

### 5.2 灭火测试原型及未来灭火关

- **领域能力**：喷射射线、有效距离/火焰根部判定、喷射效果、压制降级、恢复和复燃、灭火确认事件。
- **关卡参数**：初始火势、有效距离、压制速度、复燃等待、观察时间、场景火源与灭火器绑定。
- **关卡规则**：是否要求特定灭火器、是否检查拔销、如何计算有效喷射率与得分、扑灭后是否还要观察、何时完成/失败。
- **资产适配**：当前瓶身、软管、喷嘴和手部骨骼对应关系。归角色/道具 Prefab 适配，而非通用 Runner 或 Lua 层级查找。

当前确认窗由 FireSuppression 实现并发出 Extinguished 事件，可先保留为可配置模块能力；不同关卡的通过/评分条件应在该事件之上定义。正式第二关完整流程不能从该原型的存在推断为已完成。

### 5.3 后续疏散等关卡

当前没有对应正式配置与完整执行流程，不能据文档规划列作已实现。未来可复用移动、门、区域触发、路线与计时；出口选择、危险区、疏散优先级与评分则属于新关卡规则。

## 7. 迁移前需明确的运行语义

1. **计时基础缺口**：StageTimer 声明 OnExpired、Remaining、HasExpired，但当前没有 Update/Tick 推进计时；依赖该计时器超时的路径不会按预期自动结束。这是源码确认的问题，不代表实体题 HUD 同样不计时。
2. **暂停不统一**：RefreshFrozen 只暂停阶段计时与火焰粒子；QuizTimerHUD 用真实时间，没有接入该冻结事件；TimedStage/WaitUnscaled 也没有响应 IsPaused。FireSuppression 的逻辑时钟与表现冻结同样要分清。
3. **终止与完成合流**：StopLevel 也调用 Finish，而 Finish 总会触发 LevelFinished。迁移后要区分 Completed、Failed、Aborted，以及展示结果、选择下一关。
4. **资源/事件收尾**：已有零散 OnDisable/OnDestroy 清理，但没有关卡作用域的统一取消。比如 FreeRoamStage 的路线事件在协程正常退出处退订，StopCoroutine 不能作为完成该段显式退订代码的保证。
5. **重开边界**：结算重试调用 Begin(Entry, Config)，不是完整重载场景。需要明确重置哪些实体状态、计时、事件订阅、镜头、物品和 UI，而非只重置分数与阶段索引。
6. **事件已有、总线未有**：现有 Action/UnityEvent 是可保留的事件源；需要桥接关卡作用域与结构化载荷，不应为了“全事件化”而拆掉正常组件内调用。

## 8. 与需求文档的差距及建议顺序

当前已有目录/JSON、实体锚点雏形、组件事件、交互与消防能力。当前源码中未见统一 Lua Runtime、Entity Registry/Tag、关卡 Event Bus、Mission/Save 系统及 Addressables Resource API。Packages 中已安装 Timeline，但已查看的关卡执行链未使用 PlayableDirector/Timeline 来编排这些演出；安装依赖不能算系统接入。

建议迁移顺序：

1. **固定现有玩法基线**：办公室三题及灭火原型分别确认真实行为；统一配置来源，解决计时/暂停语义，保留既有验收依据。
2. **先拆外壳**：建立 LevelLoadRequest、LevelContext 和明确 Load/Start/Complete/Fail/Abort/Unload；把选关 ID 真正传到运行实例。
3. **建立能力边界**：Entity Binding、关卡作用域事件、计时、控制权、资源加载接口；把办公室判题/讲评/火势编排从 Runtime 移出，初期可由旧 C# 适配器执行。
4. **迁移首个关卡包**：接 Lua 并只暴露稳定 API；办公室三题的数据、绑定、规则和表现资源进入独立包；保留射线、角色控制、火焰等 C# 能力。
5. **验证不同玩法**：用灭火原型验证同一 Runtime 能运行不依赖答题/教官/四选一的关卡，再补独立资源包与更多制作工具。

验收“更加灵活”应看：新增第四道题不改结算代码；同一个办公室场景可按不同 Level ID 跑不同训练；不带火焰/答题的关卡也能启动和结束；新增关卡规则无需扩展 Runner 的 switch；退出/重开无旧事件、计时或控制锁残留。
